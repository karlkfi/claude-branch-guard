Fewer git/gh approval prompts in Claude Code, with the human kept at the protected-branch boundary.

> [!NOTE]
> **This release is mostly about prompts that carried no signal.** Ten command
> forms that used to ask now auto-approve, one write form that used to defer now
> asks, and protected branches are configurable at last. If you protected extra
> branches by editing `PROTECTED_BRANCH_RE` in the cached plugin file, that regex
> is gone — see **Upgrading**.

## Highlights

**[Protect more branches without editing the plugin](https://github.com/karlkfi/claude-branch-guard/blob/v1.5.0/README.md#configuration).** `main` and `master` were the protected set, and widening it meant editing a regex inside a cached plugin file that the next update overwrites. `BRANCH_GUARD_PROTECTED_BRANCHES` takes a comma-separated list of globs in the same `settings.json` that already holds the push policy:

```json
{ "env": { "BRANCH_GUARD_PROTECTED_BRANCHES": "release/*,integration" } }
```

Patterns match a whole branch name case-sensitively and `*` spans `/`, so one `release/*` covers `release/2.0/rc`. The list **extends** the defaults and cannot replace them, so no value — including a typo or something the hook can't parse — can unprotect `main`. Globs rather than regexes for the same reason: `fnmatch` has no malformed input to raise on, where `re.compile` does. The setting reaches every place the guard reads a branch: commits, branch-sensitive mutations, the `Edit`/`Write` check, and both push policies.

**[`git branch` is judged by the ref it targets, not by how the verb looks](https://github.com/karlkfi/claude-branch-guard/blob/v1.5.0/README.md#git-branch-what-the-session-owns-not-how-the-verb-looks).** Deleting a scratch branch you cut ten minutes ago and deleting a branch nobody else can recover were the same `ask`, which prompts constantly for the first and adds nothing to the second. A target now auto-approves when it is both **recoverable** — its tip is reachable from a remote-tracking branch or local `main`/`master`, so the worst case is one `git reset --hard <sha>` — and **private**, meaning not in the protected set. Those are independent questions and git only enforces the first, so `git branch -d main` prompts exactly like `git branch -D main`. The non-force spellings skip the recoverability probe because git already refuses the unsafe cases itself (`-d` on unmerged work, `-m`/`-c` onto an existing destination), and force is read from the whole flag set, so `git branch -d --force x` is treated as the `-D` it is.

The two probes are local, never touch the network, and may only ever turn a prompt into an approval — and only on a positive answer. Git unreachable, a ref that won't resolve, or a `git -C` pointing at another repository all land on the old behavior.

**[`git reset --hard` gets the same test, once it has nothing else to destroy](https://github.com/karlkfi/claude-branch-guard/blob/v1.5.0/README.md#git-branch-what-the-session-owns-not-how-the-verb-looks).** The command does two things — moves the branch pointer and throws away uncommitted changes to tracked files. Uncommitted work exists in no ref, so nothing can prove it recoverable and a **dirty worktree still always prompts**. With a clean one the command is just the pointer move, and an unprotected branch whose tip survives elsewhere auto-approves. Untracked and ignored files don't count as dirty, because `reset` never deletes them.

**[Editing a gitignored path on `main` no longer prompts](https://github.com/karlkfi/claude-branch-guard/blob/v1.5.0/README.md#behavior).** An ignored file holds no branch contents, so the decision would be identical on a feature branch and the prompt carried no information — `tmp/scratch.json` now defers to your normal permissions on any branch. The probe is `git check-ignore`, run only when the branch is already protected, so a feature-branch edit costs no subprocess. Only its "yes, ignored" answer withdraws the prompt; every other answer, including every answer it can't give, leaves the **ask** in place. Two cases deliberately keep asking: a file that matches an ignore rule but is tracked anyway (`git add -f`), because `check-ignore` consults the index and those edits do land on the branch; and a symlink inside an ignored directory pointing at a tracked file, because the probe resolves the path first and asks about the file the write actually lands on.

**[A write into a directory that doesn't exist yet now resolves to a branch](https://github.com/karlkfi/claude-branch-guard/blob/v1.5.0/README.md#behavior).** `git -C` on a missing directory fails, so creating `src/newdir/f.py` produced no branch and the hook deferred — on `main` as readily as anywhere. The branch is now read from the nearest existing ancestor, which is in the same repository. This is the one decision in the release that got stricter.

**Four prompts that only ever meant "yes".** `git pull` and `git pull --rebase` auto-approve on a feature branch, as `fetch`, `merge`, and `rebase` already did, and still ask on a protected one. `git stash` and `git stash pop` no longer care which branch the session is on — a stash adds no commit and rewrites no history — while `git stash drop` and `clear` still ask, because a dropped stash survives only in the reflog. `git worktree remove` auto-approves without `--force`, since git refuses to remove a worktree holding modified or untracked files. And `gh pr merge --delete-branch` stopped being classified as a branch delete: the merge lands the work before the branch goes, which is the opposite of the case that earned the prompt. `gh pr close --delete-branch` — which deletes unmerged work — still asks.

## Upgrading

**One step, and only if you edited the plugin file.** `PROTECTED_BRANCH_RE` no longer exists in `hooks/branch-guard.py`. If you widened the protected set by editing that regex in the installed copy, move the branches into `BRANCH_GUARD_PROTECTED_BRANCHES` before updating, or the update silently drops back to `main`/`master`. Nobody who left the plugin file alone has anything to do.

Third-party marketplaces have auto-update **off by default**, so an install pins its version until you turn it on or update by hand ([Upgrade](https://github.com/karlkfi/claude-branch-guard/blob/v1.5.0/README.md#upgrade)):

```bash
claude plugin marketplace update branch-guard
claude plugin update branch-guard@branch-guard
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Changes that need no action, but will be visible.** Ten forms that prompted at v1.4.2 now auto-approve, listed in **Decision surface** below. Going the other way, writing a file into a directory that doesn't exist yet **asks** on a protected branch where it previously deferred, so a session that created new directories on `main` without a prompt will now get one. Under a non-interactive permission mode that ask is a `deny`, as always.

## Decision surface

This is the largest movement in the [behavior table](https://github.com/karlkfi/claude-branch-guard/blob/v1.5.0/README.md#behavior) since 1.0. Measured by running both hooks over the same throwaway repo — a clean worktree, `origin/main` and `origin/claude/x` fetched, and `merged-topic` sitting at a tip `main` reaches:

| command | branch | v1.4.2 | v1.5.0 |
|---|---|---|---|
| `git pull` / `git pull --rebase` | feature | ask | **allow** |
| `git pull` / `git pull --rebase` | `main` | ask | ask |
| `git stash` / `git stash pop` | any | ask on `main` | **allow** |
| `git stash drop` / `git stash clear` | any | ask | ask |
| `git reset --hard <ref>` *(clean worktree, recoverable tip)* | feature | ask | **allow** |
| `git reset --hard <ref>` *(dirty worktree, or on `main`)* | any | ask | ask |
| `git branch -d merged-topic` / `-m old new` | any | ask | **allow** |
| `git branch -D merged-topic` *(tip survives elsewhere)* | any | ask | **allow** |
| `git branch -D orphan` *(tip nothing else reaches)* | any | ask | ask |
| `git branch -d main` / `-D main` / `-m x main` | any | ask | ask |
| `git branch -f backup claude/x` *(ref doesn't exist yet)* | any | ask | **allow** |
| `git worktree remove ../wt` | any | ask | **allow** |
| `git worktree remove --force ../wt` | any | ask | ask |
| `gh pr merge 5 --delete-branch` | any | ask | **defer** |
| `gh pr close 5 --delete-branch` | any | ask | ask |
| editing a gitignored path *(`tmp/scratch.json`)* | `main` | ask | **defer** |
| editing a gitignored path that is tracked anyway | `main` | ask | ask |
| writing into a directory that doesn't exist yet | `main` | defer | **ask** |

**Nothing that touches a protected branch moved.** Every form that commits to one, pushes to one, or deletes, renames, or overwrites one decides exactly as it did at v1.4.2 — `git push origin main`, `git push --force origin main`, `git push origin HEAD:main`, `git branch -d/-D main`, `git branch -f main claude/x`, `git branch -M x main`, `git commit`, `git merge`, `git rebase`, `git cherry-pick`, and `git reset --hard` on `main` all still ask, and the edit check on a tracked file still asks. The rows above that read `ask → ask` are there to say so.

Read the "any" rows as being about the ref the command *targets*, not where the session is sitting. `git stash` and `git branch -d merged-topic` auto-approve while you are on `main`, because neither one touches `main` — the stash adds no commit to it and the deleted ref is somebody else.

Two of these loosenings rest on a probe rather than on the command's shape, which is a weaker kind of evidence, so both fail toward the prompt: `branch_exists`, `tip_is_recoverable`, and `worktree_is_clean` return "couldn't tell" for every failure, and "couldn't tell" keeps the `ask`.

## Validation

**335 specs, green on Linux across Python 3.10–3.13 and on Windows under Git Bash**, on the release commit itself ([run](https://github.com/karlkfi/claude-branch-guard/actions/runs/31772714819)). Every fixture reaches the hook through `hooks/run-python-hook.cmd` — the exact command `hooks/hooks.json` registers — and that is now asserted directly rather than via a documented case count: one fixture greps the suite for any invocation outside the launcher, so a new test that shells out to the interpreter fails loudly and names its own line. The count it replaced raced between branches and never checked launcher coverage anyway, since a fixture calling the interpreter increments a count just as happily.

The suite grew by 95 cases since v1.4.2, most of them crossing axes rather than adding new commands. `classify_branch` reads two independent signals — is the target shared, is it recoverable — and the old fixtures covered each one separately: every protected assertion used a force spelling, every non-force case named an unprotected branch. Neither axis had a hole; the uncrossed cell did, and `git branch -d main` auto-approved through it with 268 cases green. Config fixtures now also carry their unset control, since `[configured] git branch -d release/1.2 -> ask` on its own would be satisfied by a form that asked unconditionally.

What the suite does not assert: it drives the hook's JSON contract in a throwaway repo, not Claude Code's own permission plumbing. It cannot tell you whether a remote-tracking ref is stale — see below.

## Security

**No advisory, and no dependencies to bump** — the hook is stdlib-only Python and the plugin ships no third-party code.

This release widens auto-approval more than any before it, so the reasoning behind each widening matters. A command is auto-approved only where the destructive outcome is either impossible (git refuses it: `branch -d` on unmerged work, `worktree remove` on a dirty worktree) or recoverable from a ref that still exists locally. The recoverability check reads local refs only, which means it trusts your last `git fetch`: a `refs/remotes/origin/x` left stale after the branch was deleted upstream still reads as recoverable. It also has no notion of a branch being shared beyond the protected set, which is exactly why the protected set is now configurable.

Guarantees stay best-effort by design. Claude Code ignores hook decisions entirely under `bypassPermissions`, so anything you need to hold unconditionally still belongs in a git `pre-push` hook or server-side branch protection.
