Fewer git/gh approval prompts in Claude Code, with the human kept at the protected-branch boundary.

> [!NOTE]
> **This release adds a prompt rather than removing one.** A push of your own worktree branch has always been auto-approved under the default `strict` policy. It still is — unless the base has moved into the same *lines* this branch edits, which now asks you to rebase first. In `dontAsk` and `bypassPermissions` that ask is emitted as a **deny**, so an unattended session that used to push will stop. Nothing else moved, no auto-approval was added, and `BRANCH_GUARD_PUSH_OVERLAP_ENABLED=false` switches the check off.

## Highlights

**[A push that is in bounds may still be built on the wrong thing](https://github.com/karlkfi/claude-branch-guard/blob/v1.8.0/README.md#push-guard).** The `strict` policy answers one question: does this push touch only the branch the worktree is on? A yes means the push is *in bounds*, and that is all it means. It says nothing about whether the branch is still built on what it thinks it is. When `origin/main` has moved into the same lines this branch edits, the merge is going to come out wrong — and under a merge queue it comes out wrong late, after the queue has validated the candidate and spent a whole check cycle on it. So the auto-approve is withdrawn and the push asks, naming the files and the fix:

```
'origin/main' has moved since this branch left it, and its new commits edit the
same lines this branch does in hooks/branch-guard.py — the merge is going to come
out wrong, and a merge queue would spend a whole check cycle finding that.
`git fetch && git rebase origin/main` finds it now — confirm before proceeding.
```

The comparison is line ranges, not paths. `push_overlap` diffs `fork..HEAD` and `fork..base` from the merge-base, so both sets of line numbers are counted in that shared ancestor and are comparable at all; `parse_hunks` reads the pre-image side of each hunk, and `hunk_range` widens it by the three lines of context a hunk carries. Edits within six lines of each other therefore meet, and edits seven apart do not. Sharing a *file* is not sharing an edit, and an overlap reported where there is none sends a session off to rebase a branch that did not need it.

Every probe fails silent. A detached HEAD, a shallow clone, an unresolvable base ref, a git too old for `merge-tree --write-tree`, or no `origin` at all returns no opinion — never "the push is fine". The cost of each is a missed catch rather than a blocked push. `--dry-run` and `--delete` land nothing on the base, so neither is checked, and the whole thing runs only where a push would otherwise be auto-approved, which is why `protected` and `off` never reach it and no verdict that already asked is disturbed.

Release branches are skipped by name — `release/*`, `hotfix-*`, `v2.1`, and the rest of `BRANCH_GUARD_RELEASE_BRANCHES`. One is cut from the base and left diverged on purpose, so telling it to rebase would publish everything merged since the tag: a wrong answer rather than a noisy one. Nothing in the commit graph separates a release branch from a stale topic branch, since both sit behind the base and ahead of the fork point, so the name is the only signal there is. That cuts the other way too, and it is the one shape deliberately excluded: a topic branch named `hotfix-typo` is never checked.

The check came from [pipe-guard](https://github.com/karlkfi/claude-pipe-guard), which shipped it first in [its PR #15](https://github.com/karlkfi/claude-pipe-guard/pull/15). branch-guard already parses `push` to destination-ref depth, so the push half lives here; pipe-guard keeps the matching `gh pr create` check ([#91](https://github.com/karlkfi/claude-branch-guard/issues/91)).

**[The hook timeout was a 2.7-hour ceiling wearing the shape of a 10-second one](https://github.com/karlkfi/claude-branch-guard/blob/v1.8.0/README.md#install).** `hooks/hooks.json` carried `"timeout": 10000`. Claude Code reads that field in **seconds**, so the registered ceiling was 10,000 seconds. The unit is invisible in the file, which is exactly what let the value sit there reading as milliseconds. It is now `60`.

That matters more than it did when the number was written, because the hook shells out to `git` now: `run_git` runs for the branch lookup, the `git branch` ownership probes, `worktree_is_clean`, `check-ignore`, the merge-tree tier, and — as of this release — the overlap diffs. A wedged repo is a reachable hang. `run_git` caps each probe at 5s, which bounds the inside; the hook timeout is the outer limit behind it, covering a hung launcher or a stuck interpreter. A five-segment `git branch -D` chain, the heaviest classifier path, measures 0.26s on a healthy repo, so 60s leaves roughly 200x headroom. Too tight would be its own bug: a `PreToolUse` hook that fails is non-blocking, so a timeout is the guard silently enforcing nothing for that call.

The fix is pinned as a startup check rather than as a comment. `test/run.sh` now aborts unless the registered timeout is a plausible seconds value (1..600), so a four-digit value fails loudly and names what it must be ([#92](https://github.com/karlkfi/claude-branch-guard/issues/92)).

## Upgrading

**No steps.** Nothing was removed, no configuration changed meaning, and no new configuration is required — the four new variables all have working defaults.

Third-party marketplaces have auto-update **off by default**, so an install pins its version until you turn it on or update by hand ([Upgrade](https://github.com/karlkfi/claude-branch-guard/blob/v1.8.0/README.md#upgrade)):

```bash
claude plugin marketplace update branch-guard
claude plugin update branch-guard@branch-guard
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Changes that need no action, but will be visible.** Every decision that moved belongs to the new check; the last two below are the rest of what you could notice.

* **A push of your own branch can now ask.** Only when the base has moved into the lines this branch edits. If it never has, you will not see this — the base sitting where the branch left it is the common case and returns immediately.
* **In `dontAsk` and `bypassPermissions` that ask is a `deny`.** An unattended session pushing a branch whose base moved underneath it will be stopped rather than prompted. That is the existing fail-safe applying to a new ask, not a new policy, but it is the sharpest edge of this release. If it blocks a pipeline you need unblocked, `BRANCH_GUARD_PUSH_OVERLAP_ENABLED=false` is the switch, and the break-glass is deliberately not: no push form is in `OVERRIDABLE_GIT`, and unlike the denials that motivated `BRANCH_GUARD_OVERRIDE`, this one is not a dead end — it names its own fix, and rebasing is the thing to do anyway.
* **`git push && rm -rf x` now asks where it used to defer.** An overlap ask beats the all-segments rule. This is the one place the check adds friction instead of withdrawing an approval, and it is deliberate: the overlap is a property of the push rather than of what is chained after it, and a defer would lose the catch outright in a session that has allowlisted `git push`.
* **A `master`-default repo needs no configuration.** The base ref is derived from the clone's own `origin/HEAD`, falling back to `origin/main` only when the clone never set that symref.
* **A wedged hook now gives up after 60 seconds instead of 10,000.** No decision changes. What changes is how long a stuck `git` can stall a session before the call falls through to the ordinary permission flow.

## Decision surface

Measured by running the v1.7.0 hook and this one over the same throwaway repo: `origin/main` moved after `claude/x` forked, with both sides editing `file.txt` unless a row says otherwise. The default `strict` policy except where noted.

| command | v1.7.0 | v1.8.0 |
|---|---|---|
| `git push` *(base moved into the same line)* | allow | **ask** |
| `git push origin HEAD` *(same)* | allow | **ask** |
| `git push --force` *(same)* | allow | **ask** |
| `git push && rm -rf x` *(same)* | defer | **ask** |
| `git push` *(same, `auto` or `default` mode)* | allow | **ask** |
| `git push` *(same, `dontAsk` or `bypassPermissions`)* | allow | **deny** |
| `git push` *(base moved 7 lines away)* | allow | allow |
| `git push` *(base moved in a different file)* | allow | allow |
| `git push` *(base has not moved)* | allow | allow |
| `git push --dry-run` *(base moved into the same line)* | allow | allow |
| `git push` *(on `release/1.2`, base moved into the same line)* | allow | allow |
| `git push` *(on `hotfix-typo`, base moved into the same line)* | allow | allow |
| `git push` *(same, `BRANCH_GUARD_PUSH_OVERLAP_ENABLED=false`)* | allow | allow |
| `git push` *(same, `protected` or `off` policy)* | defer | defer |
| `git push origin main` *(protected target)* | ask | ask |
| `git status` | allow | allow |

**One rule added, nothing removed.** Every decision that moved landed on **ask** — or on **deny** in the two modes where an ask converts — and no row moved to **allow**. The protected-branch set, the push policies, the classifier, the `git branch` ownership tier, and the break-glass are all untouched by this release. The `allow → allow` rows are there to say which pushes did *not* start prompting, since that is the question a reader of this section actually has.

## Validation

**458 specs, green on Linux across Python 3.10–3.13 and on Windows under Git Bash**, on the release commit itself ([run](https://github.com/karlkfi/claude-branch-guard/actions/runs/32211635265)). Every fixture reaches the hook through `hooks/run-python-hook.cmd`, the exact command `hooks/hooks.json` registers, and two fixtures assert that directly. A `CASE_FLOOR` of 430 catches a suite that silently collapses because setup failed or a section exited early, and a second startup check now reads `hooks.json`'s own timeout and aborts unless it is a plausible seconds value.

The suite grew by 46 cases, all of them the new check, and the crossing is the point rather than the count. The decision turns on several independent questions, so the fixtures cross them: same line versus 4 apart versus 7 apart versus a different file, base moved versus not, `--dry-run`/`-n`/`--delete`, `strict` versus `protected` versus `off`, a protected target answered ahead of the check, `dontAsk` denying against the `auto` control, the opt-out with both a true and a garbled control, release names by default glob and by configured glob including the extend-only case, an unresolvable `BASE_REF` versus a configured one, and `OVERLAP_IGNORE` crossed against whether the merge genuinely conflicts. Every config-dependent case carries its unset control, because a fixture that asks under a configured value proves nothing on its own — a form that asked unconditionally would satisfy it too.

A suite written from the same mental model as the code asks the same half of the question and passes green with the hole open. So the check was mutated deliberately:

| mutation | cases red |
|---|---|
| ranges always meet / never meet | 1 / 21 |
| context widening removed | 3 |
| ignored paths discounted unconditionally | 1 |
| `overlap_ignore` ignored entirely | 2 |
| release branches unrecognised / globs replace rather than extend | 5 / 1 |
| `--dry-run`/`--delete` treated as a real push | 3 |
| opt-out ignored / any value read as false | 2 / 22 |
| probe gate removed | 1 |
| any `--- ` line taken as a file header | 2 |
| `base_ref` env var ignored | 2 |

Two survived the first run. **A removed line beginning with `--` comes out of a diff as `--- …`**, and reading one as a file header files every later hunk under a path that does not exist, so the real overlap goes unseen. Catching it needed a fixture with a deleted `-- DROP TABLE` line *and* a second hunk after it — the same shape that started as a survivor in pipe-guard's own run. **The `fork == tip` early return is behavior-preserving**: a base sitting on the fork point has an empty diff and shares no path anyway. It is a short-circuit saving two `git diff` processes, not a correctness guard, and the code now says so out loud so nobody writes a fixture pretending otherwise.

</details>

What the suite does not assert. It drives the hook's JSON contract in a throwaway repo whose `origin/main` is written straight into `refs/remotes`, so nothing touches a network and no fixture exercises a real fetch, a real remote, or a real merge queue. The check reads local refs, which means it trusts your last `git fetch`: a base that moved since then looks unmoved, and the push is auto-approved. It also compares line *ranges*, not semantics — two edits six lines apart are reported as meeting whether or not they interact, and a rename or a moved function reads as unrelated. Treat it as a cheap prompt to rebase, not as proof the merge is clean.

## Security

**No advisory, and no dependencies to bump** — the hook is stdlib-only Python and the plugin ships no third-party code.

**No auto-approval was added anywhere**, which is the claim the decision table above is there to back: every row that moved landed on `ask` or `deny`, and the set of commands that run without a prompt at v1.8.0 is a strict subset of the set at v1.7.0. This release only takes an auto-approve away, in one narrow case, and the one place it adds friction beyond that (`git push && rm -rf x`, which used to defer) moves toward asking rather than away from it.

The timeout fix is a hardening rather than a patched vulnerability. A `PreToolUse` hook that times out is non-blocking, so the guard enforces nothing for that call — a ceiling that reads as 10 seconds and is actually 10,000 leaves a wedged `git` able to stall a session for hours instead of failing fast into the ordinary permission flow.

Guarantees stay best-effort by design. The hook parses the Bash command Claude runs, so it only governs Claude's `Bash` tool, and Claude Code ignores hook decisions entirely under `bypassPermissions`. Anything you need to hold unconditionally still belongs in a git `pre-push` hook or server-side branch protection.
