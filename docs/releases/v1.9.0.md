Fewer git/gh approval prompts in Claude Code, with the human kept at the protected-branch boundary.

> [!NOTE]
> **No decision changed in this release.** Every command that was auto-approved at v1.8.0 still is, and every command that asked still asks — measured across 22 forms by running both hooks over the same repos. What changed is that one existing ask now also tells the *model* what to do about it, so a session whose overlap push you approve will know to rebase instead of learning only that the call went through.

## Highlights

**[The rebase instruction now reaches the model, not just the prompt](https://github.com/karlkfi/claude-branch-guard/blob/v1.9.0/README.md#push-guard).** v1.8.0 added the overlap check: when the base has moved into the same lines your branch edits, the auto-approve is withdrawn and the push asks, naming the files and ending in a rewrite — `git fetch && git rebase origin/main`. That reason reaches you at the permission prompt and stops there. Approve it, and the session pushes onto the stale base it was just told to rebase onto, and the merge queue spends the check cycle the reason existed to save. The outcome the check exists to prevent, reached by way of a prompt somebody said yes to.

The cause is in how Claude Code routes a hook's reason. On `deny` the reason becomes a `blockingError` and the model reads it. On `ask` it becomes the permission prompt's text and is delivered nowhere else:

```js
case"deny": u.permissionBehavior="deny",
  u.blockingError={blockingError:e.hookSpecificOutput.permissionDecisionReason||...};
case"ask":  u.permissionBehavior="ask";   // reason -> prompt text, nothing else
```

Measured rather than inferred, on Claude Code 2.1.220. A census of 837 local session transcripts found 2,245 `PreToolUse` `ask` verdicts carrying a reason; in 2,232 of them the reason appears nowhere in the model-visible tool result. The 13 exceptions are non-interactive runs where the ask had already been converted to a refusal. Independently: all 69,869 `PreToolUse` hook-success attachments carry an empty `content` field, because the reason is recorded in the hook's `stdout`, which is Claude Code's own log rather than a channel to the model.

So the overlap verdict now also returns the rewrite as `hookSpecificOutput.additionalContext`, which does reach the model. Claude Code queues it while the hook's output is read — before the permission prompt is constructed — so it lands whichever way you answer. The verdict itself is unchanged: still an `ask`, still a `deny` in the unattended modes, still withdrawing an auto-approve rather than blocking a push that was already going to be reviewed.

Internally the verdict is tagged `ask-rebase` rather than `ask`, the way `ask-shared` already carries "the cause is a protected branch" through the classifier. The tag came out unliftable on both existing locks without new code: `is_overridable` accepts only a plain `ask`, and no `push` form is in `OVERRIDABLE_GIT`, so the break-glass reaches it through neither.

**It is the only verdict that carries a context, and that is a design rule rather than an accident of scope.** Every other ask here is settled by being answered — a protected-branch commit, a `reset --hard`, a `gh repo delete`. Their cause is a judgement for you to make, and once you have made it there is nothing left for the model to act on, so a context would be text it cannot use. The overlap ask is the one whose cause names work to do, which is why it is the one that goes stale the moment the prompt is approved. Adding a second one is a claim that its cause outlives the prompt too. The `deny` path deliberately carries none either: a denial already delivers the reason to the model, and repeating it would say the same thing twice ([#96](https://github.com/karlkfi/claude-branch-guard/issues/96)).

## Upgrading

**No steps.** Nothing was removed, no configuration changed meaning, and no new configuration was added. `BRANCH_GUARD_PUSH_OVERLAP_ENABLED=false` still switches the whole check off, context included.

Third-party marketplaces have auto-update **off by default**, so an install pins its version until you turn it on or update by hand ([Upgrade](https://github.com/karlkfi/claude-branch-guard/blob/v1.9.0/README.md#upgrade)):

```bash
claude plugin marketplace update branch-guard
claude plugin update branch-guard@branch-guard
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Changes that need no action, but will be visible.**

* **A session may now rebase after you approve an overlap push.** That is the point of the release, and it is the one behavior a reader should expect to look different. The model receives the `git fetch && git rebase <base>` line and can act on it; at v1.8.0 it received nothing and carried on. If you approved the push precisely because you wanted it to land unrebased, say so — the context tells the model what the guard found, not what you decided.
* **The context arrives whichever way you answer.** Claude Code queues it before showing the prompt, so rejecting the push delivers it too. That is deliberate: a rejected overlap push is exactly the case where the rebase is the next thing to do.
* **Nothing else emits one.** A protected-branch ask, a destructive-command ask, and the unattended `deny` all carry no `additionalContext`, and the release ships three fixtures that fail if any of them starts to.

## Decision surface

Measured by running the v1.8.0 hook and this one over the same throwaway repos and diffing the emitted `permissionDecision`: `origin/main` moved after `claude/x` forked, with both sides editing `file.txt` unless a row says otherwise, under the default `strict` policy except where noted.

| command | v1.8.0 | v1.9.0 | context to model |
|---|---|---|---|
| `git push` *(base moved into the same line)* | ask | ask | **yes** |
| `git push origin HEAD` *(same)* | ask | ask | **yes** |
| `git push --force` *(same)* | ask | ask | **yes** |
| `git push && rm -rf x` *(same)* | ask | ask | **yes** |
| `git push` *(same, `auto` mode)* | ask | ask | **yes** |
| `git push` *(same, `dontAsk`)* | deny | deny | no |
| `git push` *(same, `bypassPermissions`)* | deny | deny | no |
| `git push` *(base moved 7 lines away)* | allow | allow | no |
| `git push` *(base has not moved)* | allow | allow | no |
| `git push --dry-run` *(same)* | allow | allow | no |
| `git push` *(same, `BRANCH_GUARD_PUSH_OVERLAP_ENABLED=false`)* | allow | allow | no |
| `git push` *(same, `protected` policy)* | defer | defer | no |
| `git push origin main` *(protected target)* | ask | ask | no |
| `git commit -m x` *(feature branch)* | allow | allow | no |
| `git status` | allow | allow | no |
| `git reset --hard` | ask | ask | no |
| `git branch -D scratch` | ask | ask | no |
| `git clean -fd` | ask | ask | no |
| `git restore file.txt` | ask | ask | no |
| `gh repo delete o/r` | ask | ask | no |
| `git log \| head -5` | allow | allow | no |
| `git log > f` | defer | defer | no |

**Zero decisions moved.** Not one row differs between the two columns. A release that withdraws an auto-approve can claim only that the prompt-free set has not grown; this one leaves that set identical. The protected-branch set, the push policies, the classifier, the `git branch` ownership tier, and the break-glass are all untouched. The only column that changes is the third, and it is new output rather than a new verdict.

## Validation

**467 specs, green on Linux across Python 3.10–3.13 and on Windows under Git Bash**, on the release commit itself ([run](https://github.com/karlkfi/claude-branch-guard/actions/runs/32431209284)). Every fixture reaches the hook through `hooks/run-python-hook.cmd`, the exact command `hooks/hooks.json` registers, and three fixtures now assert that directly — the count moved from two because reading the new field needed a third helper, and a helper that bypassed the launcher would have quietly cost every one of its cases its launcher coverage.

The suite grew by 9 cases. Four assert the context is present and carries the base, the rewrite, and the statement that the prompt is not the model's to answer. Three are controls that pin the "only verdict" claim, and they are the half that does the work: a suite proving only that the context appears would pass just as happily against a hook that attached one to everything. The sharpest is a protected-target push *in the same overlap repo* — same repo, same overlap, same files, only the verdict differs — alongside the unattended `deny`, whose reason already reaches the model, and a push with no overlap at all. The last two cases cover the chained `git push && rm -rf foo`, where the context has to come from the same verdict the reason did rather than from whichever segment happened to ask, and the break-glass declining to lift the new tag.

<details><summary>Mutation-checked: three mutations, and each kills a different third of the block</summary>

A green assertion that cannot go red proves nothing, so the check was mutated deliberately before being trusted:

| mutation | cases red |
|---|---|
| context dropped at the call site | 5 |
| context attached to every ask, `ask-shared` included | 1 |
| context leaked onto the `deny` path | 1 |

The second and third each turn exactly one control red, which is what those controls exist for — and neither is reachable from the other, since the `ask`/`deny` split lives inside `confirm()` while the verdict split lives at the combine site. Mutating one call site would have left the other hole open.

</details>

Verified end-to-end as well, which the suite cannot do: a headless Claude Code run against a real repo whose base had moved into the branch's lines, with the real hook registered the way `hooks.json` registers it, returned the context to the model verbatim.

```
RESULT: {"got_context": true, "quote": "branch-guard stopped this push to ask about a stale base: 'origin/main' has"}
```

What none of this asserts. Headless Claude Code converts a hook `ask` into a refusal, so the *approved* path — the exact case this release is about — was never observed directly. It rests on the ordering in Claude Code's own bundle, where the context is pushed into the conversation while the hook's output is read and before the permission decision is acted on, so the answer cannot affect whether it lands. That is a code reading, not a measurement, and it is the one claim here that is not backed by a run. The measurements that *are* backed by runs — the census, the surface diff, the mutations, the end-to-end — are described above with their numbers.

## Security

**No advisory, and no dependencies to bump** — the hook is stdlib-only Python and the plugin ships no third-party code.

**No auto-approval was added anywhere.** Zero decisions differ between v1.8.0 and v1.9.0 across the 22 forms in the table above. A release that only adds an output field cannot widen what runs without a prompt, and the table is there so a reader does not have to take that on trust.

The new field discloses nothing the prompt did not already show. `additionalContext` restates the cause the permission prompt displays — the base ref, the overlapping paths, and the rebase command — so the model learns what you were about to be shown, not anything more. It is emitted only on the `ask` path, so an unattended `deny` adds no output at all.

Guarantees stay best-effort by design. The hook parses the Bash command Claude runs, so it only governs Claude's `Bash` tool, and Claude Code ignores hook decisions entirely under `bypassPermissions`. Anything you need to hold unconditionally still belongs in a git `pre-push` hook or server-side branch protection.
